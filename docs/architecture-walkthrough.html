01

Start with the mental model

Ignore the Windows-specific machinery for a moment. At a systems level, this is a stateful service hidden behind a stateless-looking command line.

An agent observes a window, receives compact handles such as @e5, and then acts on those handles. The daemon is the memory between “observe” and “act.”

The key architectural choice: element refs are not selectors and are not serialized Windows objects. They are keys into the daemon’s in-memory table of live UI Automation elements. That is why the daemon must outlive each CLI process.

Simple verbs

Daemon keeps

The attached window, snapshot generation, monotonically increasing ref counter, and live element dictionary.

Windows does

Cross-process automation

UIA providers expose semantic controls and supported patterns; COM carries the calls across process boundaries.

03

CLI & REPL: the translation edge

The CLI is intentionally thin. It converts user intent into typed protocol records and converts responses back into human or machine output.

One-shot mode

Simple, composable, slower

Every command starts a new CLI process and named-pipe connection. The daemon remains alive, so automation state survives. Ideal for humans and occasional calls.

REPL / batch mode

Persistent client connection

One CLI process reads lines from stdin and holds its daemon connection. This avoids repeated process startup and connection overhead for agent loops.

One-shot command: first runAuto-spawn only happens when the pipe is absent

Why the REPL is more than a convenience

The daemon only accepts one client connection at a time. A REPL deliberately owns that connection for its lifetime, giving it predictable ordering and low latency. The tradeoff is equally deliberate: a second client for the same session waits until the pipe becomes available. Parallel agents should use different --session names.

# One process, one connection, many requests
agent-windows repl --session writer
attach --window "Notepad"
snapshot -i
fill @e1 "hello from the batch"
press Ctrl+S
exit

Fail-fast batch semantics: the first unsuccessful response ends the REPL with exit code 1. This prevents an agent from continuing a stale plan after the UI has diverged.

04

The daemon: one place owns reality

The daemon is a background copy of the same executable. It is not a Windows Service; it is a user-session process, started on demand and scoped by a session name.

Why a daemon? Because a shell command is ephemeral, but the useful automation objects are stateful and process-bound.

DaemonHost
Creates the server pipe, accepts one client, reads one line at a time, stamps elapsed time, and handles shutdown.
transport loop
RequestDispatcher
Validates protocol semantics, normalizes refs, maps typed requests to session methods, and converts exceptions into stable errors.
policy + routing
FlaUiSession
Owns UIA3Automation, the target window, app handle, ref table, generation, and next ref index.
state + effects

Invariant

One session, one daemon

The server uses a single pipe instance. If another process already owns the pipe name, a duplicate daemon exits.

Invariant

Requests are serialized

One client is served at a time; within that connection, each request is fully handled before the next line is read.

Invariant

State changes are ordered

Attach, snapshot, click, and close cannot race inside one daemon. The simple loop is the concurrency control.

05

Named pipes: local IPC without a port

A named pipe is a kernel-managed byte channel addressed by name. It gives unrelated processes a bidirectional connection without TCP, port allocation, or firewall configuration.

↔

Analogy: a named pipe is closer to a local Unix domain socket than to a file. Windows exposes it in the special namespace \\.\pipe\; the name identifies a rendezvous point, not data on disk.

Address

\\.\pipe\agent-windows.default

The suffix is the logical session name. --session qa maps to an independent agent-windows.qa pipe and daemon.

Framing

One JSON object per line

The pipe is a stream, so the application needs message boundaries. A newline is the delimiter; reader and writer use ReadLine/WriteLine.

wire example · conceptual 
→ client to daemon
{"cmd":"click","ref":"e5","button":"left","doubleClick":false,"timeoutMs":10000}

← daemon to client
{"ok":true,"payload":{"kind":"ack","detail":"clicked"},"elapsedMs":2.3}

The subtle “absent vs busy” problem

A pipe that exists can still reject an immediate connection because another client—usually a REPL—owns the single server instance. Treating that as “no daemon” would spawn a duplicate that can never acquire the same pipe name.

AProbe

WaitNamedPipeW(name, 0) checks instantly.

→
BClassify

FILE_NOT_FOUND means absent; busy or timeout still means exists.

→
CDecide

Spawn only if absent. If busy, wait for the existing daemon.

→
DConnect

Retry in 500 ms windows, up to the 10 s deadline.

Why JSON here? The messages are small, local, and command-oriented. Human readability and a stable compatibility surface matter more than maximum throughput. Source-generated serialization removes reflection-heavy runtime setup while keeping the protocol inspectable.

06

UI Automation & COM, without the lore

This is the Windows-specific heart of the system. UI Automation provides the semantic model; COM is largely the plumbing that makes cross-process objects callable.

UI Automation: a semantic view of an application

Microsoft UI Automation (UIA) is an accessibility and automation framework built into Windows. Instead of reading pixels, a client asks the target application for a tree of elements: windows, buttons, edit fields, menus, tabs, documents, and their properties.

Property

What is it?

Name, control type, AutomationId, bounds, enabled state, focus, and whether it is off-screen.

Pattern

What can it do?

Value, Toggle, ExpandCollapse, Selection, Scroll, Window, and Transform are capability interfaces.

Tree

Where is it?

Parent/child structure mirrors the logical UI, not necessarily the app’s visual or code hierarchy.

COM: object calls across process boundaries

COM—the Component Object Model—is a Windows binary interface system. The useful intuition is that a UIA element returned from another application behaves like an object, even though the implementation may live in that other process. COM proxies and marshaling move method calls and property values across the boundary.

What a property read really meansFlaUI hides the COM interface details, not the cost

The performance implication: a property access that looks like a cheap .NET getter may be a cross-process round trip. Walking 500 elements and reading 10 properties individually can become thousands of COM calls.

Bulk caching is the central snapshot optimization

SnapshotBuilder activates a UIA CacheRequest containing the properties and patterns needed for the whole subtree. Windows can populate them in a bulk cross-process operation. The local tree walk then reads cached data. If a provider rejects caching, the implementation falls back to a live walk.

PathBehaviorTradeoff
Cached walkFetch subtree properties and pattern state together; retain full live element references.Fast path; minimizes COM chatter.
Live fallbackEnumerate children and read properties directly; ignore elements that vanish mid-walk.More compatible, potentially much slower.
Selection fixupsRead selected item names after the cache scope closes.Targeted extra calls for data that is awkward to cache.
Why can an element “vanish” during a read?
UI trees are live. A menu may close, a list may re-render, or a window may be destroyed between enumeration and property access. COM then reports an unavailable element. The implementation turns this into dropped snapshot nodes or a stale-ref error instead of leaking COM exceptions through the public protocol.
Where does FlaUI fit?
FlaUI is a .NET wrapper around the UI Automation APIs. It supplies typed automation elements, pattern wrappers, input helpers, capture utilities, and UIA3 integration. It reduces API friction, but the runtime behavior—cross-process calls, provider differences, stale elements, privilege boundaries—still comes from Windows UIA.
Why mix UIA and direct Win32 calls?
UIA is ideal for semantic control interaction, but enumerating every desktop element is expensive. The project uses EnumWindows for fast top-level window discovery and direct process/token APIs for process name and elevation. It then converts the chosen HWND into a UIA window for deeper work.
07

Snapshots & refs: a safe temporary address space

A snapshot converts a volatile, verbose UIA tree into a compact value tree for reasoning—while the daemon keeps the live elements needed for action.

What crosses the pipe

Plain data: role, name, AutomationId, value, states, bounds, children, and a short ref string.

- window "Untitled - Notepad" [@e21]
  - document "Text editor" focused [@e1]
  - menubar automationId=MenuBar
    - menuitem "File" collapsed [@e5]

What stays in the daemon

The dictionary maps bare ids to live FlaUI AutomationElement instances.

_refs = {
  "e1"  → AutomationElement(document),
  "e5"  → AutomationElement(menuItem),
  "e21" → AutomationElement(window)
}
Ref lifecycle across snapshotsIDs increase forever within the daemon lifetime

Why refs are never reused

On each snapshot, the old dictionary is replaced, but the numeric counter continues upward. The dispatcher can therefore distinguish two failure classes:

stale-ref

“I issued this before.”

The numeric id is lower than the next id but absent from the current table. The caller must re-snapshot.

unknown-ref

“I never issued this.”

The id is beyond anything the daemon has generated. Usually a typo or a ref from another session.

Safety property: an old ref can never silently select a different element after a new snapshot. This trades convenience for determinism—a strong choice for an AI-facing tool.

Snapshot filtering

--interactive keeps interactive controls plus the non-interactive ancestors needed to preserve context. --depth caps traversal. --scope @e3 starts from a live element from the previous snapshot, then replaces the active table with refs from that scoped snapshot.

The action pipeline: semantic first, physical second

Actions resolve a ref, wait for it to be usable, and prefer a UIA capability pattern. Mouse and keyboard input are fallback mechanisms where appropriate.

Actionability is a small resilience layer

Ref-based actions poll until an element is enabled and on-screen or the timeout expires. This handles common transient states—animations, delayed enablement, menu opening—without requiring every caller to build retry loops.

Pattern actions

Often background-safe

Value, Toggle, Selection, and ExpandCollapse ask the control to perform an operation. They usually do not require foreground focus.

Input actions

Focus-sensitive

Keyboard and mouse input interact with the desktop’s global input state. window focus is important before press or keyboard fallbacks.

Protocol & errors: one compatibility surface

The wire model is typed inside the codebase and explicit on the wire. Requests use a cmd discriminator; responses use a stable envelope.

Request

Polymorphic command record

{"cmd":"snapshot", ...} selects the concrete request type. The dispatcher validates cross-field rules after deserialization.

Response

Always one envelope

Success carries a typed payload. Failure carries errorCode and message. Daemon handling time is attached uniformly.

success and failure shapes 
{
  "ok": true,
  "payload": { "kind": "snapshot", "root": { … }, "generation": 2 },
  "elapsedMs": 50.1
}

{
  "ok": false,
  "errorCode": "stale-ref",
  "message": "@e4 is not part of the most recent snapshot …",
  "elapsedMs": 0.4
}

Error translation protects the abstraction

Expected domain failures become AutomationException with a stable code. The dispatcher catches them and returns protocol failures. Any unexpected exception is converted to internal-error. Raw COM, I/O, and library exception types do not become part of the caller contract.

Caller issue

bad-request

Malformed ref, missing selector, invalid action arguments, or non-positive timeout.

State issue

no-target / stale-ref

The command is valid but incompatible with current daemon state.

Platform issue

elevated-target

Windows integrity levels prohibit the cross-process automation request.

Review note: the protocol is local-only today, but it should still be treated as versioned behavior. Tests pin JSON shapes and error contracts because agents depend on exact, machine-readable semantics.

Operational realities on Windows

The clean abstraction has edges. These are not incidental bugs; they follow from Windows security, process, and input models.

Integrity levels

Elevation is a hard boundary

A non-elevated process cannot automate an elevated target. Attach detects this early and returns elevated-target.

Packaged apps

Launch may hand off

Store/UWP stubs can start another process and exit. The launcher may have no main window; attach by visible title instead.

Desktop input

Focus is global state

Keyboard fallbacks and press target the foreground desktop. Pattern-based operations are safer when available.

Build lifecycle

The daemon locks its executable

A running daemon can block replacing built bits. Stop it before rebuilds or manual publish cycles.

Packaging adds one small indirection

The Windows CLI targets net10.0-windows, but .NET’s tool packaging rejects Windows-specific target frameworks. The package therefore installs a plain net10.0 launcher that checks the OS and starts the bundled Windows payload. A self-contained publish bypasses the shim and requires no installed runtime.

Staff-level design review

The architecture is intentionally small and coherent. These are its strongest decisions, current constraints, and the questions worth carrying forward.

Strong decision

Single state owner

No distributed ref state, no cross-process UIA serialization, and deterministic ordering within a session.

Strong decision

Monotonic refs

Stale observations fail loudly instead of mutating the wrong control.

Strong decision

Platform quarantine

Most behavior remains fast to test and easy to reason about without a desktop.

Tradeoffs to accept consciously

ChoiceBenefitCost / ceiling
One client per sessionSimple concurrency and deterministic state transitions.A long REPL monopolizes the session; no concurrent readers.
In-memory refsFast, direct actions on live objects.Daemon restart loses target and ref state by design.
Newline JSONDebuggable, stable, easy to produce from agents.No streaming payloads, backpressure protocol, or schema negotiation.
Poll-based waitsProvider-agnostic and easy to understand.Can be less efficient or responsive than UIA event subscriptions.
Full cached snapshotFar fewer COM round trips.Large or pathological trees may still be expensive in time and memory.

Questions for the next architecture review

Do sessions need authentication or explicit pipe ACLs?

Today the trust model is local-user tooling. Revisit before using the protocol across identities, services, or remote boundaries.

Should protocol versions become explicit?

Tests protect compatibility inside one release line, but a version field would help mixed CLI/daemon upgrades and clearer evolution.

When does one-client serialization stop scaling?

If several consumers must share a target, consider a queued broker rather than adding parallel access to live session state.

Which waits deserve event-driven implementations?

High-frequency or long-running waits may benefit from UIA events, provided provider inconsistencies are contained behind the session interface.

What telemetry is needed beyond elapsedMs?

Cache fallback rate, COM failure categories, snapshot node counts, and action retry duration would expose real reliability bottlenecks.

Bottom line: the system succeeds by putting state and Windows complexity behind one narrow process boundary. The CLI stays disposable, the Core stays portable, and the daemon turns volatile UI objects into a controlled observe–act loop with explicit failure semantics.
